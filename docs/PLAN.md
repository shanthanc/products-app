# Products App — V1 Implementation Plan

## Context

Implements INTENT.md's V1 — create a product and list products — over
React/TypeScript → Spring Boot → PostgreSQL, as three vertical slices. Each slice is split into
test-first stories and is built, verified and reviewed on its own. Points INTENT.md leaves
unspecified are recorded under **Decisions** at the end.

`./gradlew check` (plus `npm run lint && npm run build` when the client changed). Each slice ends
with the API → DB tests green and a manual UI → API → DB check in the browser. Stop for review
after each slice; the owner commits.

## API contract

Base path `/api`. Requests and successful responses are `application/json`; errors are
`application/problem+json` (RFC 9457, Spring's `ProblemDetail`).

| Endpoint | Request | Success | Errors |
|---|---|---|---|
| `POST /api/products` | `{"name": "P1"}` — only `name` is read; a client can't set `id` | `201`, `{"id": "<uuid v7>", "name": "P1"}` | `400` missing/blank name or malformed JSON, `415` wrong content type, `500` unexpected |
| `GET /api/products` | — | `200`, `[{"id": "...", "name": "..."}, ...]`, newest first; `[]` when empty | `500` unexpected |

Error body (the UI relies on `status`, `detail` and, when present, `errors`):

```json
{
  "type": "about:blank",
  "title": "Bad Request",
  "status": 400,
  "detail": "Invalid request content.",
  "instance": "/api/products",
  "errors": [ { "field": "name", "message": "Name is required" } ]
}
```

A 500 has the same shape without `errors`, and a generic `detail`
("Something went wrong. Please try again.").

Implementation: one `@RestControllerAdvice` extending `ResponseEntityExceptionHandler`, which
already renders Spring MVC errors as `ProblemDetail`. It adds `errors` for validation failures and
a catch-all for 500s. 4xx are logged as a single `WARN` line; 5xx as `ERROR` with the exception.
Nothing internal (exception messages, SQL, class names) reaches the response.

## Database

`api/src/main/resources/db/migration/V1__create_products.sql`:

```sql
create table products (
    id   uuid primary key default uuidv7(),
    name text not null check (btrim(name) <> '')
);
```

- The `check` mirrors `@NotBlank`: the database rejects empty or whitespace-only names too.
  Names are stored as sent; nothing is trimmed.
- Flyway runs at startup (and for each test context against Testcontainers).
- `spring.jpa.hibernate.ddl-auto=validate`: Hibernate only checks the entity against the migrated
  schema; it never creates or alters tables.
- Applied migrations are never edited; changes go in `V2__...`.

**Id generation.** Postgres assigns the id via the `uuidv7()` default. The entity never sets it:

```java
@Entity
@Table(name = "products")
class Product {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private UUID id;

    @Column(nullable = false)
    private String name;
    // protected no-arg constructor, constructor(name), getters
}
```

`IDENTITY` tells Hibernate the database assigns the key during insert: the id is left out of the
`insert` and the generated value is read back. S1.1's test proves this works (the returned id is a
v7 UUID matching the stored row). If it can't be made to pass, stop and ask; the fallback is to
perform the insert with `JdbcClient` (`insert ... returning id, name`).

## Client

- Scaffolded from the `react-ts` template; nothing added beyond it.
- `vite.config.ts`:

  ```ts
  export default defineConfig({
    plugins: [react()],
    server: {
      port: 3000,
      strictPort: true,
      proxy: { '/api': 'http://localhost:8080' },
    },
  })
  ```

- App code only calls relative URLs (`/api/products`), so there's no API URL to configure and no
  CORS: Vite proxies locally; a reverse proxy does the same elsewhere.
- `src/api/products.ts` is the only module using `fetch`, and defines the `Product` and error types.
- `App` owns the product list and re-fetches after a create; `ProductForm` owns only its input and
  submit state; list keys are product ids; `useEffect` is used only for fetching.

## Configuration and environments

| Setting | Where | Local default | Override |
|---|---|---|---|
| Postgres db / user / password | `docker-compose.yml` | `product` / `products` / `products` (local only) | `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD` |
| Postgres host port | `docker-compose.yml` | `127.0.0.1:20028` | `POSTGRES_PORT` |
| API datasource | `application.yml` | `jdbc:postgresql://localhost:20028/product` | `SPRING_DATASOURCE_URL`, `_USERNAME`, `_PASSWORD` |
| API port | Spring Boot default | `8080` | `SERVER_PORT` |
| Client dev port and proxy | `vite.config.ts` | `3000` → `http://localhost:8080` | dev-only |

```yaml
# api/src/main/resources/application.yml
spring:
  application:
    name: products-api
  datasource:              # local defaults; other environments use SPRING_DATASOURCE_*
    url: jdbc:postgresql://localhost:20028/product
    username: products
    password: products
  jpa:
    hibernate:
      ddl-auto: validate   # schema comes from Flyway only
    open-in-view: false
```

```yaml
# docker-compose.yml
services:
  db:
    image: postgres:18.6
    environment:
      POSTGRES_DB: ${POSTGRES_DB:-product}
      POSTGRES_USER: ${POSTGRES_USER:-products}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:-products}   # local-only default
    ports:
      - "127.0.0.1:${POSTGRES_PORT:-20028}:5432"
    volumes:
      - db-data:/var/lib/postgresql   # Postgres 18 image volume path
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U ${POSTGRES_USER:-products} -d ${POSTGRES_DB:-product}"]
      interval: 5s
      timeout: 3s
      retries: 10
volumes:
  db-data:
```

V1 configures the local environment only. **Dev, QA and prod** would run the same artifacts
(the API jar and the built `client/dist`), differing only in environment variables: datasource
settings from the platform's secret store and the server port. Each environment has its own
Postgres, migrated by Flyway at startup. Nothing per-environment is committed, and Spring profiles
are added only if an environment needs different behavior, not just different values.

## Testing

| Layer | How | Docker |
|---|---|---|
| API contract and validation | `@WebMvcTest` + `MockMvc`, service mocked: status codes, error format, field errors, 500 masking | no |
| API → DB | `@SpringBootTest` + Testcontainers Postgres: requests through the full stack, then assert on the table; database constraint checks | yes |
| Service | Covered by the API → DB tests (it only delegates); unit tests added if logic appears | — |
| UI | `npm run lint` + `npm run build` (type check); main flow checked manually per slice | — |

Tests use a real Postgres (not H2, which has no `uuidv7()`):

```java
@TestConfiguration(proxyBeanMethods = false)
class TestcontainersConfiguration {
    @Bean
    @ServiceConnection
    PostgreSQLContainer postgresContainer() {
        return new PostgreSQLContainer(DockerImageName.parse("postgres:18.6"));
    }
}
```

Commands (from `api/`):

| Command | Runs | Needs Docker |
|---|---|---|
| `./gradlew test` | unit and `@WebMvcTest` tests | no |
| `./gradlew integrationTest` | tests tagged `integration` | yes |
| `./gradlew check` | everything | yes |

```groovy
// build.gradle (added in S1.2)
tasks.named('test') {
    useJUnitPlatform { excludeTags 'integration' }
}
tasks.register('integrationTest', Test) {
    description = 'Tests that need Docker (Testcontainers).'
    group = 'verification'
    testClassesDirs = sourceSets.test.output.classesDirs
    classpath = sourceSets.test.runtimeClasspath
    useJUnitPlatform { includeTags 'integration' }
    shouldRunAfter 'test'
}
tasks.named('check') { dependsOn 'integrationTest' }
```

The split is added in S1.2, with the first test that doesn't need Docker. Gradle 9 fails a test
task that finds no tests, so splitting earlier would break the build.

## Implementation notes

- **Postgres 18 volume path:** mount at `/var/lib/postgresql` (not `/data`), or data won't survive
  recreating the container. S0.1 verifies it.
- **Boot 4 names:** `spring-boot-starter-webmvc` (not `-web`), `@MockitoBean` (not `@MockBean`),
  `testcontainers-postgresql`. Older snippets won't compile; generated Initializr and create-vite
  code is the reference.
- **`ddl-auto=validate`** fails startup if entity and migration disagree — intended.
- **`strictPort`:** the client fails if :3000 is taken instead of silently using another port.

## Decisions

Points INTENT.md leaves unspecified:

1. **Package:** group `com.shanthan`, root package `com.shanthan.products`.
2. **"Without a name":** missing, `null`, empty and whitespace-only names are rejected at the API
   (`@NotBlank`) and the database (`not null` + `check`). Names are not trimmed.
3. **List order:** newest first, by id (UUIDv7 is time-ordered).
4. **List response:** a plain JSON array.
5. **Frontend tests:** none automated in V1; type check, lint and a manual browser check per slice.
6. **Unknown fields in the create request:** ignored; only `name` is read.
7. **After a create:** the input clears and the list re-fetches; no extra UI messages.
