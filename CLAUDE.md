## What is being built

A products app: a React UI where users create a product and see the list of saved products, backed by a REST API and PostgreSQL. V1 scope is only **create a product** and **list products**. Don't build anything past the current scope (no edit/delete, pagination, auth, etc. unless the scope changes).

## Planned stack (from INTENT.md)

- **Frontend:** React + TypeScript, built with Vite. The Vite dev server proxies API calls to the backend. Node 26, pinned in `.nvmrc`.
- **Backend:** Spring Boot 4 (latest GA from Initializr) on Java 25, built with Gradle (Groovy DSL). Commit the Gradle wrapper; `.gitignore` already un-ignores `gradle-wrapper.jar`.
- **Database:** PostgreSQL 18, started with Docker Compose (image version pinned in the compose file).
- **Migrations:** Flyway, version managed by Spring Boot. The schema changes only through versioned migrations, never by hand and never via JPA/Hibernate auto-DDL.

## Data model

One table, `products`:
- `id` — UUID v7, **generated by the database** (Postgres 18 native `uuidv7()`), primary key. The app does not generate ids.
- `name` — text, required (enforce `NOT NULL` in the database as well). Stored **normalized**: leading and trailing whitespace trimmed, uppercased; whitespace between words kept (`" Some Product Name "` → `SOME PRODUCT NAME`). At most 50 characters, counted as typed; longer is a `400` (DB `CHECK` `products_name_max_length`).
- Names are **not unique**; duplicates (after normalization) are allowed. The database enforces normalization with a named `CHECK` (`products_name_normalized`).
- The JPA entity must not generate its own id; it must read back the id Postgres assigns on insert.

## Architecture rules

- Strict layering, UI → API → database. The UI never talks to the database. Business rules live in the backend; the UI only handles input and rendering.
- Use standard Spring Boot and React/Vite project layouts and patterns. No custom abstractions or unusual folder structures.
- API packages are by layer, under `com.shanthan.products`: `controller`, `service`, `repository`, `entity` (JPA entities), `model` (request/response records), `exception` (domain exceptions, no HTTP types), `handler` (`@RestControllerAdvice`, maps exceptions to HTTP). Tests mirror these packages; tests that span all layers (API → DB) go in the root package.
- Client folders by responsibility, under `client/src`: `types` (data shapes such as `Product`, `ProblemDetail`), `api` (the only code that calls `fetch`; also turns errors into user-readable messages), `validation` (plain functions, no React; the UI copy of the API's rules), `components` (rendering and local UI state only). Add `hooks` only when components need shared data-fetching state; no `utils`, `services` or `store` folders.
- Validate at every layer, but the API is the source of truth: the UI validates for fast feedback, the API rejects bad input (e.g. a missing name) with a clear error, and the database enforces critical constraints.
- JSON over HTTP, with consistent status codes and **one consistent error response format** that the UI relies on. Errors return a user-safe message to the client and are logged on the server with enough context to diagnose.
- Connection details and ports come from configuration with local defaults. No hard-coded secrets (`.env` files are gitignored; `.env.example` is allowed).
- Add a dependency only when it clearly saves more than it costs.
- Build as a thin vertical slice: get the smallest working path through UI → API → DB before deepening any layer.
